05 / QA samples

How I document quality.

Examples of how I write test cases, bug reports, SQL checks and automation, using generic sample data.

TEST CASE · TC-01FUNCTIONAL

Leave request cannot exceed available balance

Precondition
Employee has 2 days of annual leave balance
Priority
High
  1. Sign in as the employee and open Leave Application.
  2. Select Annual Leave for 3 working days.
  3. Submit the request.

Expected: Submission is blocked with a message that names the available balance (2 days). No request is saved.

TEST CASE · TC-02ACCESS CONTROL

Approver sees only their own team's requests

Precondition
Two managers with separate teams; each team has a pending request
Priority
High
  1. Sign in as Manager A and open the approval inbox.
  2. Search for the request raised by Manager B's team member.

Expected: Only Manager A's team requests are listed; the other request cannot be opened or approved.

BUG REPORT · BR-01MAJOR

Overnight shift leave hours calculated as negative

Environment
QA build, Chrome
Severity
Major · Priority High
  1. Employee on a 22:00–06:00 shift applies for hourly leave 23:00–02:00.
  2. Check the calculated leave hours before submitting.

Expected: 3 hours.

Actual: −21 hours; the end time is treated as the same day.

BUG REPORT · BR-02MINOR

Generic message when a required field is empty

Environment
QA build, Chrome
Severity
Minor · Priority Medium
  1. Open a request form, leave a mandatory field blank and submit.

Expected: The missing field is highlighted and named in the message.

Actual: “Please fill all fields” appears without identifying the field.

DATA CHECK · SQL-01SQL

Screen balance matches the database

After an approval, I confirm that the balance shown on screen equals the stored values.

-- Balance must equal entitled minus availed
SELECT employee_id, leave_type,
       entitled, availed, balance,
       entitled - availed AS expected_balance
FROM   leave_balances
WHERE  employee_id = :emp_id
AND    balance <> entitled - availed;  -- expect 0 rows
AUTOMATION · PW-01PLAYWRIGHT

Repeatable end-to-end leave submission

A simple Playwright (Python) script I use to re-run the same scenario across builds.

from playwright.sync_api import expect

def test_submit_leave(page):
    page.goto(BASE_URL + "/login")
    page.fill("#username", "test.employee")
    page.fill("#password", PASSWORD)
    page.click("text=Sign in")
    page.click("text=Leave Application")
    page.select_option("#leaveType", "Annual")
    page.click("text=Submit")
    expect(page.get_by_text("Request submitted")).to_be_visible()
All samples use generic data and simplified screens. No client data, screenshots or internal requirements are shown.
06 / Testing approach

From requirement to release.

Understand

Review requirements, roles, conditions and dependencies; raise questions early.

Design

Write positive, negative, boundary and workflow scenarios with clear expected results.

Execute

Run the tests, record actual results and capture evidence, including SQL checks.

Report

Log defects with reproducible steps, severity and expected versus actual behaviour.

Retest

Verify each fix against the original defect conditions before closing it.

Regress

Check related screens and workflows for unintended impact before release.
